# Brief: Project Release Notes

## Scope

This brief explains how a project can organize release note knowledge before a maintainer writes a final release announcement.

## Target Link

- `library/knowledge/04_targets/project_release_notes.md`

## Current Answer

Release notes become more useful when source material is staged instead of collapsed directly into announcement text. The source notes show three durable needs: separate user-visible changes from internal maintenance, preserve evidence for each change, and give maintainers a compact synthesis before final writing.

## Key Points

- Keep source notes traceable until final writing.
- Separate user-visible changes from internal maintenance.
- Use compact briefs before creating long-form release note books.

## Evidence Base

- `library/knowledge/05_maps/project_release_notes.yaml`

## Sources

## Current Understanding

The knowledge-target model supports that by keeping raw notes in `knowledge/01_sources`, source-derived artifacts in `knowledge/02_artifacts`, target proposals in `knowledge/03_seeds`, target identity in `knowledge/04_targets`, evidence membership in `knowledge/05_maps`, compact synthesis in `knowledge/06_briefs`, long-form treatment in `knowledge/07_books`, and later use feedback in `knowledge/08_feedback`.

## Constraints And Tensions

- Maintainers need a compact view, but the compact view must still point back to source material.
- Larger releases may justify a book, while smaller releases may only need a brief.

## Do Not Assume

- This brief does not write a final release announcement.
- This brief does not prove every release needs a long-form book.

## Confidence

`medium`, because the example is grounded in one small source and intended mainly to validate the structure.
